# 构造检查的两方法配对试验

先提交了 `fixture_holdout_v1.json`，冻结 `Document.canContainContent` 和 `SAXHandler.startElement`、预期行为和修复次数。两者独立于此前的 Element 调参，但同属 JDom。每个目标共用一次生成的初始测试，失败后各组最多修复一次。对照使用现有修复提示模板，两组均关闭修复知识检索。构造检查组额外执行目标调用前的代码，并把结果交给同一修复模板。此运行使用小样本入口。

| 方法 | 共同初始结果 | 现有修复组 | 加构造检查组 |
|---|---|---|---|
| `Document.canContainContent` | 通过，直接调用目标并捕获第二根元素对应的 `IllegalAddException` | 复用原测试 | 构造检查通过，复用原测试 |
| `SAXHandler.startElement` | 编译失败，初始测试缺少 `SAXHandler` 导入 | 修正包名与导入，JUnit 通过 | 构造前缀也报相同的编译错误。修正后前缀和完整测试均通过 |

逐项审查表明，Document 的原意图保留。SAX 两组都直接调用 `startElement`，并断言当前元素的局部名和命名空间 URI。两组均未直接断言该元素是文档根，因此只覆盖冻结意图的一部分。JUnit 通过与意图完整保留分开记录。

两组均有 2 个整套通过的目标，准入覆盖一致，目标行覆盖 31/91，分支覆盖 18/80。共有 4 次请求、8,944 token。共用生成 3,016 token，现有修复组额外使用 2,852，构造检查组额外使用 3,076。构造检查组的 3 次额外本地执行共约 3.98 秒，包含编译、JUnit 和覆盖率工具。提供商 token 统计与本地计时分开。

这次只遇到普通编译错误，没有出现可执行但构造异常的初始测试。因此本次没有观察到构造检查的增量收益，也无法据此判断它对真实构造异常的效果。
