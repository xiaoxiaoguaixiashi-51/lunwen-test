# 对象作用域线索：近邻、Full材料与预算门槛复核

2026-10-30。本轮零API，没有实施新约束生成器、改变既有研究计划或提高预算。结论是收窄候选准入条件，不宣布找到新算法。

## 1 不能把对象关系约束本身称为创新

- [TELPA论文§3.2](https://arxiv.org/html/2404.04966v2)已有对象构造调用链和分支依赖上下文。固定提交b93c4ff610fd3506d760d50767954af7b6713c92的Java construct_context实际合并目标方法、分支依赖及选定调用链，再补类声明/字段/构造器。此处核对的是选定函数，不是完整运行。
- [IntTestGen论文§3.1—3.2](https://arxiv.org/html/2605.26851v2)已有项目使用片段、类型索引、字段前置条件、调用协议与两阶段修复。不能断言其必然无法处理namespace案例。本轮没有定位可确认的官方实现入口，不等于断言其未开源，也不把论文描述当作完整代码审计。
- [Korat相关MIT学位论文的官方摘要](https://dspace.mit.edu/entities/publication/ce661fc6-3b5d-4187-817c-c828dc650466)已说明通过Java谓词/不变量生成合法结构化输入。对象关系合法性不是LLM时代才出现的新问题；本轮没有取得Korat原论文PDF全文，不伪称做了源码/性能复现。

因此“加入对象约束/构造合法对象/检查前置条件”只能是问题定位或工程能力。若以后提出新机制，必须说明自动获得何种新证据、如何避免错误泛化、为什么简单上下文/已有工具不能达到相同效果，并接受反例否定。

## 2 同一个问题，项目自身已经保存简单上下文

在当前JDom源码定位到Element.addNamespaceDeclaration调用Verifier.checkNamespaceCollision；原项目TestElement.testSetNamespaceAdditional明确测试了同前缀、不同URI的冲突，以及同一namespace可重复声明的不同结果。TestNamespaceAware包含相关作用域与父子对象测试。

jdom_existing_context_locations_20261030.json保存四文件SHA、选定14个方法/重载的起始行和参数类型；不导出第三方整份源码。它证明简单“相关实现＋原项目用法/测试检索”有可用材料，不证明把这些材料给模型后必然成功。

该基线必须先比较。若它已解决同样问题，就没有理由增加复杂约束层；不能以故意遗漏相关上下文的弱基线证明创新。约束提炼若只把现成测试改写成一句提示，也不能自动称为新方法。

## 3 当前保存Full材料没有支持性复现

saved_full_overlap.json用两份已备份的10月重建初始试跑原件，去掉中断占位行并核对6个不同目标。两个run metadata均明确知识、StaticGuard和反馈开关开启。Parser.processArgs在保存运行中通过；Element.getNamespacesInScope并不在这六目标中。

这不是最新完整41方法Full，也不是把中断/续跑合成新的独立重复；旧代码版本、阶段与测试源码仍按归档分别保留。现有证据不能声称namespace冲突在启用约束的Full中仍频繁存在，也不能因没有该目标就宣布不存在。上一轮真实失败线索仍来自历史A3，必须保留这种限制。

正式或定向付费试验前，应先形成可审阅的新上下文/预算协议：优先检查现成方法级源码、相关声明与用法片段的简单方案，按同样来源和资源口径比较；改变规格须另存新版本，不能改写已用v1或只给差结果放宽预算。

## 本阶段决定

暂不将对象作用域约束认定为核心贡献，不实现生产原型，不转向通用断言研究。继续沿高依赖主线，先让强简单上下文基线和可执行预算条件成立，再判断是否仍存在需要新机制的、可重复的依赖构造失败。若仅缺项目已有用法或属于A3撤掉现有约束的后果，就不叠加组件。

所有JSON均为新审计产物，不覆盖旧试验。当前只改变我们对证据与下一步顺序的判断，不改变RQ1/RQ2、A1/A2/A3或论文中的结果数字。
