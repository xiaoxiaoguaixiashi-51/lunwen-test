## 已落实的三项检查

1. 41方法的使用台账：6个明确用于本轮开发，另外35个没有足够材料证明未调参/未审阅，均不允许称独立留出集。v1/v2方法ID集合匹配，不意味着目标签名和参考分母未变化。readiness.json保存逐项证据边界，不将“未找到使用记录”写成“未使用”。
2. 初始生成、失败种子修复、覆盖反馈的开关矩阵：Full全保留；A1初始检索关闭且两个后续检索入口都明确禁用；A2只禁覆盖缺口检索；A3初始配置及两个后续阶段都禁StaticGuard/项目约束。反馈YAML本身不自动控制这些CLI开关。矩阵是准备规格，不是实际运行开关已生效的证据。
3. 发现并修复初始编译循环的末轮无验证修复：原实现最多编译3次，却在第3次失败后又做一次模型修复，返回未验证源码并保持失败状态。现仍最多编译3次，仅在后面还有编译机会时修复，因而最多2次编译修复请求。单次编译上限时不调用修复；成功路径不变。两项新增回归先复现失败，再在修正后通过。历史结果与旧调用成本原样保留，不回溯删除或重标。

## 公平预算仍有的实质差异

- 初始KCF是Task/Plan/Generation及可能的编译修复；RAG基线一次生成。相同模型和max_tokens不是同计算预算。后续种子修复、覆盖生成和失败修复也必须计入KCF成本，不能只数初始生成。
- GenerationAgent和RAG部分调用显式指定8192，不能以为改YAML max_tokens就统一控制所有请求。需要一处共享的预算门禁，并记录拒绝/耗尽状态；当前还没有跨阶段硬预算执行器。
- EvoSuite生成按去重的项目/类启动，共35个项目类，而评估清单有41方法。TypeHandler、CSVFormat、CollectionUtils、XPath、Format涉及共享类；同一次类生成的成本不能向每个方法重复记为独立生成，也不能拿60秒/类直接宣称60秒/方法。readiness.json保存完整类—方法映射，预算必须在项目类组或明确的分摊规则下比较。
- 已有exec并集合并工具仅做离线后处理，覆盖反馈每轮仍有旧XML计数逻辑，尚未完整统一。仅修最终报表不能证明每轮停止/选目标也采用精确探针并集。
- 初始Pipeline的“success”主要是编译成功，RAG的success是非空输出，二者不是同一指标；正式结果必须经同一独立执行/覆盖层统计，不能直接对比两个runner的completed列。
