## 目的和范围

先使用已经审计的 CSV、Codec、JDom、Windward 四个失败种子验证处理差异和运行成本，明确标记为开发诊断。不得从四例筛掉难例、借用后来人工修好的测试或把四例称独立验证集。现有通过的 CLI/Collections 种子不混入修复成功率分母。

## 四种处理：只有知识选择不同

| 处理 | 知识选择 | 能回答的问题 |
|---|---|---|
| N | 空列表 | 额外经验相对于相同源码/日志的增量价值 |
| F | 对所有案例提供相同的三条完整记录 | 是否只是一般经验提示有用，而非按查询选取有用 |
| L | 现有 repair_test 的全文词项交集 Top-3 | 当前实际选择机制 |
| T | 同一查询、同一记录、无监督 TF-IDF 余弦 Top-3 | 简单标准排序是否已经足够；不是候选创新 |

F 不另写“优化过的通用指南”，避免同时改变内容、格式和选择方式。固定条目由全部 ID 的 SHA-256 排序选前三，排序键为 `(sha256(UTF8("kcf-diagnostic-fixed-v1:" + id)), id)`，只看 ID、不看失败或结果。得到固定顺序：

1. `commons-lang-stringutils-levenshtein`
2. `commons-lang-extended-message-format`
3. `commons-lang-arrayutils-to-map`

单一固定集合有选择方差，F 结果只能解释这个集合，不推断所有静态提示。若后续需要多组固定集合，必须先修订规格和预算，不能看结果后更换有利集合。

L 和 T 的查询严格为 `fqcn + "\n" + method + "\n" + phase + "\n" + failure[:6000] + "\n" + original_test[:6000]`。L 评分复用已有函数，无类名额外奖励；并列按 ID 升序，无正分则空列表。T 使用同一 tokenize，文档为每条原始 JSON 的 `json.dumps(record, ensure_ascii=False)`；词表只从 12 条记录建立，idf=`ln((1+12)/(1+df))+1`，TF 为词项是否出现的 0/1 值，文档/查询向量分别 L2 归一化，按余弦降序、ID 升序，零分排除。不得根据四例删停用词、调权重或调公式。

为避免分数标签成为额外干预，四种处理均不向模型展示 retrieval_score，只展示已有 compact_record 内容字段，保留稳定 ID，统一 JSON 序列化、字段顺序和提示模板。L 原始分数另外记日志。因此该诊断 L 不是旧请求的逐字复制；不能直接把旧输出当作本轮 L 结果。

## 预算与公平口径

- 四例 × 四处理 × 三次独立请求 = 最多 **48 次**请求。每次从同一原始失败种子重新开始；没有第二轮修复或覆盖反馈。重复序号不是声称服务端支持随机种子。
- 每个 case/repeat 块内，将 N/F/L/T 按 `sha256("kcf-diagnostic-order-v1:" + case_id + ":" + repeat + ":" + arm)` 排序，逐个执行；记录实际时间以识别服务漂移。不为某处理追加调用、重试、早停优待或人工提示。
- 每请求相同 system prompt、源上下文、原测试、原日志、最大输出 8192 token 和最大输入 12000 token。完整提示先离线渲染并测量；任一处理超限则整个案例暂不执行，另行修订共同上下文裁剪规则。不能只截断某处理的知识或源码以硬凑预算。
- F/L/T 最多三条完整知识；相同知识槽位上限 2048 输入 token。超限也在发送前阻止，不按结果截断。N 不加无意义填充。**统一上限不等于实际成本相等**：记录各处理实际输入/输出、缓存计费、延迟、检索与 Java 执行成本，报告效果和成本共同变化，不宣称严格等 token 实验。
- 对应输入上界 576000 token、输出上界 393216 token，是预算上限而非耗用预测；总计费单价需按实际服务确认，不能把机器租金等同 API 成本。未取得可核验 tokenizer/token 计数方案时不能声称预算门禁已实现。
- API 超时/限流/账户错误不偷偷重试，也不默默缩小分母。原样记录并同时报告意向运行全部 48 单元及技术有效子集；缺失影响处理平衡时不得据此判断机制优劣。补跑需单独记录原因与预算。

## 指标与审查

主要指标：每次请求产物是否编译、完整测试套件是否运行通过、是否通过独立语义审查；三者分开报告。运行通过但删除断言/测试、改测其他方法、添加跳过/绕路，或只把 actual 抄成 expected 而无源码依据，不能算有效修复。沿用现有 repair_integrity 自动门禁，加隐藏处理标签的人工源码复核；单人复核要如实说明，不冒充独立评审。

次要指标：目标方法覆盖率（固定参考分母、执行隔离）、原测试体有无实质变化、错误是否重复、知识相关性/使用证据、实际 token/时间/调用成本。无语义变化可以作为诊断标签，不能不经执行直接当通过/不通过。失败产物的覆盖与通过产物覆盖分别标明；不择优挑一次，不对失败缺失值缩小覆盖分母。合并执行覆盖时用真实 exec 合并，不用 XML 最大值近似探针并集。

输出逐 case/arm/repeat 的状态表及三个重复的全部值，提供同 case 的配对差异。四个方法不是 48 个独立目标，重复请求也不是新增项目；不据此做全数据泛化或稳定显著性声明。

## 继续/收缩判断

- 如果 N、F 与 L 相近，先判断源码/日志是否已足够；不能据小样本直接断言知识无用，也不能跳过验证宣称复杂筛选必要。
- 如果 F 可重复地不劣于 L，优先检验查询选择机制的边际价值，而不是把一般提示收益写成检索创新。
- 如果 T 优于 L，只说明普通排序值得修正；TF-IDF 本身不作为新贡献。
- 只有在具体失败链出现可核查必要条件冲突后，再讨论适用性原型；排序噪声和 oracle 错误不是同一问题。
- 如值得扩展，先清点其余 35 方法此前是否已用于代码调试、结果审阅或提示调参，再冻结独立样本和重复数；不能仅因它们未在这四例中出现，就宣布未见过。固定开发/评估边界后才运行后续验证。
