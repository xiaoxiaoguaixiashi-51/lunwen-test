新增离线强简单基线：整类源码F0有11/41条第一分析提示超12000；只保留准确目标方法/部分声明F1、再加同类直接名称调用候选F2，41目标均完成提取且首提示均在上限内，目标方法做了AST往返身份核验。没有调用模型或接入Pipeline，不证明相关依赖信息充分、能编译或测试效果提高；F2不包含跨类guard、完整调用图、项目测试或评估答案。继续先检验简单方案，不将它称为新算法。证据以仓库最新 `results/minimal_source_context_20261030` 为准。

## 近邻研究：继续独立核查的入口

以下为此前讨论形成的判断和来源入口。涉及当前实现、可运行性或新颖性时重新核查，不能将旧交接当作独立阅读证据。

| 工作 | 论文或公开实现 | 需核对的重叠与限制 |
|---|---|---|
| TELPA | https://arxiv.org/html/2404.04966v2 ; https://github.com/chenyangyc/TELPA | 已有 Java 适配线索；不能将“支持 Java”当成差异点，需实测适配和可比性 |
| CoverUp | https://arxiv.org/html/2403.16218v3 ; https://github.com/plasma-umass/coverup | 已有覆盖引导、执行验证和迭代改进，需核对机制层面重叠 |
| ChatUniTest | https://github.com/ZJU-ACES-ISE/ChatUniTest | 已有上下文构建和生成—验证—修复流程 |
| TestSpark | https://github.com/JetBrains-Research/TestSpark | 已有生成、执行、覆盖和工具集成 |
| KTester | https://github.com/SYSUSELab/KTester ; https://arxiv.org/abs/2511.14224 | 项目结构/用法及测试知识、先设计再生成已有重叠 |
| IntTestGen | https://arxiv.org/html/2605.26851v2 | 构造使用片段、字段前置条件、符号/协议/迭代修复约束；未完整运行其实现，不猜测其一定无法处理本地案例 |
| MuMuTestUp / MockBench | https://arxiv.org/html/2605.19265v1 ; https://arxiv.org/html/2610.14629v1 | 变异反馈增强断言与mock行为忠实度已被研究，不能将“通过不等于有效”本身写成创新 |
| Korat等结构输入生成 | https://dspace.mit.edu/entities/publication/ce661fc6-3b5d-4187-817c-c828dc650466 | 对象不变量、合法结构化输入是成熟问题，不能仅改成LLM提示就当新机制 |

“依赖分析＋检索＋多智能体＋编译修复＋覆盖反馈”的组合本身不能直接作为充分创新。比较应落到必要条件如何抽取、如何证明冲突、如何安全回退、失败如何归因及成本如何计算等可检验机制。

## 五阶段与交付物

1. **版本与证据审计**：定位历史实验对应代码/提交、知识库、方法清单、runner、开关和日志；抽查成功及失败样例，补查近邻研究。输出版本对应表、失败归因表和相关工作对照表。已完成部分直接复用，剩余材料缺失须说明。
2. **最小原型**：只在当前候选有问题证据与实质近邻差异时进入，不强制实现旧的三值筛选。先验证可处理范围、误拒/误排及成本，不立即做复杂路径求解或对象合成。
3. **小规模验证**：针对候选设计能否定它的强简单对照。V0/V1/V2/V3是已停止的知识适用性候选的历史方案，只有新证据使其重新准入才使用，不能默认下一步执行。诊断对照不自动替换既定RQ2。
4. **正式实验**：冻结配置和知识库，公平预算比较、独立重复运行、未参与调参样本评估；形成新版 RQ1/RQ2、成本/误差分析和复现材料。新消融定义需具体说明并与用户确认。
5. **修改论文**：按实际结果修订贡献、方法、相关工作、消融和有效性威胁，再确定投稿目标。不能在机制和效果未验证时先写成确定结论。

早期“阶段 1 约 2–4 工作日、原型约 1–2 周”仅为当时估计，不能当作承诺或当前进度。小规模可先考虑三次独立运行估计方差，正式重复次数依据方差、成本和研究问题决定，三次本身不保证充分。

## 实验控制与归因

- 各机制版本固定知识内容、目标方法、模型及预算口径；简单过滤基线也使用相同基础知识与环境。
- 全部生成、筛选、修复计入调用数、token 和耗时，同时记录编译率、运行率、覆盖、失败类型、误排除和回退。
- 开发调参样本与最终评估样本分开，排查知识库泄漏评估答案。
- 核查 TELPA Java 或其他强基线的实际可运行性、预算和评估一致性，再决定如何纳入，不凭仓库名称承诺可比。
- StaticGuard 与适用性筛选是否独立，需要代码审计和对照；不要将 A3 框架冲突案例直接归因为检索知识错误。
- 若关键问题证据不足，优先补齐“目标能力—检索条目—生成源码—确定性失败”关联。无冲突、归因不清或简单基线已足够时，缩减机制与论文主张。

## 对用户报告的五个问题

审计或阶段评估时，明确回答：

1. 最终实验版本是否定位，缺少什么？
2. 旧日志能否串联检索知识、生成代码和具体错误？
3. 真实失败原因是什么，候选筛选能解决哪一部分？
4. 与 StaticGuard、TELPA 等工作的实质重叠和差异是什么？
5. 是否值得进入原型/下一阶段；若不值得，依据是什么，更小调整是什么？
